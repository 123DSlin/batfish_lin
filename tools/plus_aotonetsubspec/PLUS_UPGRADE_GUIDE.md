# Plus AutoNetSubspec 升级指南

## 1. 升级目标

Plus 为一项允许修改的配置计算**保持目标网络性质的允许范围**。给定原配置、目标字段或配置行、网络性质和链路故障预算，固定其他配置，允许路由重新收敛到模型允许的稳定状态。子规约应接受所有已证明满足性质的改配，包括改变下一跳、路径、起源或路由属性的改配。同时，任何存在合法失败结果的改配都应被排除。

这个目标可以用 Q1 的一个字段说明。C、I 都能交付同一个前缀，删除 T 的 ISP prepend 后，部分双故障场景从 C 改走 I，前缀仍可达。因此 Q1 应允许 `enable=false`。同样的改配如果违反指定终点、隔离或容量性质，相应子规约就应排除它。字段不变、选路不变和性质不变是三个不同的约束，其中性质决定 Plus 的允许范围。参见 [Demo1/Q1](../../../DEMOIDEA/demo1/Q1/README.md) 和 [Demo2](../../../DEMOIDEA/demo2/README.md)。

本目录的起点是 [当前 Symbolic pipeline](../netsubspec/README.md) 的工作区副本，覆盖切片、一致性检查、分支求解、结果聚合及可选的流量投影。Plus 的实现和测试放在此目录，原 pipeline、Traverse 和已有实验作为独立对照。第一版验收范围为单前缀、单 VRF、确定性 eBGP、双向物理链路的 at-most-`k` 故障预算，以及一个已支持的 prepend 字段或配置行。反馈、多稳定状态、ECMP、新策略类型和联合 SR 权重分阶段加入。

## 2. 正确性约定

### 配置、故障与合法状态

- `h` 是释放的目标配置。字段级只释放该字段，行级同时释放该行的相关字段。对于 prepend，分别支持释放 `cost`、释放 `enable` 和同时释放二者。省略语句的验收使用 `enable=false`，并依据编码检查其与有效追加次数为零的关系。
- `F` 是共享的物理链路故障赋值。一次链路故障同时影响两个方向，设备切片、转发和未来的流量执行都使用同一组 `F`。连接逻辑里的局部接口状态、选路变量和 ECMP 选择不计入链路预算。
- `M(h,F,s)` 描述一个合法的联合路由和转发状态 `s`。它包含协议选路、路由通告、跨设备依赖和相关的转发语义。所有设备共享同一个 `h` 和 `F`。如果性质量化 ECMP 的每条路径，`s` 还应包含合法的包级转发选择。
- `P(s)` 描述用户声明的性质。前缀可达检查流量是否实际到达允许的终点。仅宣告该前缀、选中一个看似正确的起源，或中间路由器的下一跳符合预期，都不能代替交付检查。

在合法字段取值域 `D` 内，对每个预算允许的故障 `F`，允许配置 `h` 的条件为：

```text
safe(h) = D(h) AND forall F:
    budget(F) => ((exists s: M(h,F,s))
                  AND NOT (exists s: M(h,F,s) AND NOT P(s)))
```

第一项确保每个场景都有合法状态。编码缺失、未支持的语义或模型无解需要单独报告。第二项排除所有合法失败结果。同一故障允许两个结果时，一条成功路径不能掩盖另一条失败路径。第一版虽使用确定性场景，投影接口也应能表达这一合同。稳定态验收只覆盖模型内的稳定结果，收敛过程属于独立的性质。

### 结果怎样才算合理

| 结果 | 判定 |
|---|---|
| **正确** | 输出范围内不存在预算内的合法失败状态，且合法故障都有模型。 |
| **完整** | 在声明的支持范围和编码语义内，每一个满足上述条件的配置都在输出公式中。 |
| **已验证的保守范围** | 仅在实现明确支持保守输出且已经证明其正确时使用。报告标明可能漏掉安全改配的原因和范围。 |
| **不支持、模型不完备或求解不确定** | 区分原因和受影响目标，保留诊断。超时、`UNKNOWN`、残留内部符号和无法证明的切片边界都不能生成精确允许范围。 |

## 3. 现有实现的改动重点

| 位置 | Plus 的设计 |
|---|---|
| [1_smt_slicer.py](1_smt_slicer.py) 和 [slicing/bgp.py](slicing/bgp.py) | 复用设备的 import、BEST、export、forwarding、故障及配置方程。为目标构造依赖闭包，保留改配后可能进入选路的候选。原配置的分支表继续作为证据和查找入口。 |
| [consistency/seed_builder.py](consistency/seed_builder.py) 和 [consistency/route_binder.py](consistency/route_binder.py) | 用原配置 seed 验证参考 RIB。为 Plus 增加独立构造路径，受影响的 BEST、IMPORT、转发和邻居状态由共享设备方程产生。只有通过边界验证的原 guard 才能进入新求解。 |
| [3_branch_simplifier.py](3_branch_simplifier.py) | 当前分支投影用原 `selection_guard` 限定场景，并保留选路快照。Plus 增加按性质投影的入口，输入为连接后的设备语义、字段域、故障预算和目标性质。复用配置分组和投影工具。 |
| [4_branch_intersection.py](4_branch_intersection.py) | 复用配置公式格式与等价化简机制。Plus 先在每个共享故障场景中判断合法选路结果，再投影出允许范围。确定性 Q1 在一个场景内接受到 C 或 I，随后再覆盖全部故障。 |
| [utils/util_symbolic.py](utils/util_symbolic.py) | 复用 SMT 解析、量词构造、求解和等价查询。优先消去设备内部状态，并用求解器核对最终只含目标字段的公式。 |
| [5_traffic_subspecification.py](5_traffic_subspecification.py) | 后续接收由 Plus 选路产生的转发条件。以同一个 `h`、`F` 和网络状态计算交付与链路负载，再对路由字段及 SR 权重作联合投影。 |

Plus 分开处理两个用途。一致性检查回答“固定为原值时能否复现原状态”。性质投影回答“释放后哪些状态合法、哪些仍满足性质”。原状态观测可用于前者，也可用于已经证明不受改动影响的边界。

## 4. 切片、竞争和边界

1. **从目标字段找变化源。** 从配置到策略的判断、属性赋值和出入口通告建立依赖。以真实协议和策略语义确定候选可用、接受和传播的条件。旧配置下拒绝、未胜出、或在旧 guard 下超出故障预算的分支，仍需检查改配后是否可行。
2. **在每个受影响的选路点保留竞争输入。** 候选的属性可保持不变而胜负发生变化。Demo3 中，T 的通告让 Y 对该路由的 local-pref 从 200 降到 80，来自 B 且 local-pref 为 150 的路由因此胜出。B 的通告作为边界输入保留，Y 的 BEST 在切片内重新计算。X 则说明同一个下一跳仍可能导出不同 community。
3. **让传播和汇合共用边界变量。** 将发送端 BEST、定向 EXPORT、接收端 IMPORT 以及下游选择连接起来。多个分支汇合时保留它们在相同 `h`、`F` 下的关联。存在通告反馈时，把互相依赖的设备联立处理。
4. **证明边界后再缩小范围。** 边界摘要应保留参与下游接收、比较和转发的联合关系。已有 guard 必须在整个目标取值域和故障预算内成立。可先用完整语义作参照，分别检查完整模型是否有减少切片后失去的合法边界状态，以及切片是否引入不可实现的新组合。证明不足时，保留上游方程并继续扩展。若资源不足，标记对应目标未完成。
5. **剪枝以新条件为准。** 仅在 `D(h)` 与故障预算下证明不可实现时删除候选。对端口或通告的比较应包含是否存在，以及在存在时会影响接收端的全部属性。验收不能只比较下一跳或最终可达位。

[Demo3 的四设备验收](../../../DEMOIDEA/demo3_fanout/result/competition/report.json)已在固定出口策略下从七份设备方程缩到 T、X、Y、Z 四份，认证了包括 B→Y 在内的切片边界。该原型用全量模型作证据，提供了第一版可复用的验证方法。规模版应逐步用局部边界证明替代对全网参照的依赖。

## 5. 测试矩阵和验收

| 用例 | 验收条件 |
|---|---|
| **Q1 的安全换路** | 其他字段固定时，输出允许删除 T 的 ISP prepend。分别检查 `enable=false` 及适用的数值边界。核对 29 个故障场景下的实际终点。 |
| **同拓扑不同性质** | 对同一 Q1 改配分别验证“到 C 或 I”和“只到 C”。前者允许改走 I，后者返回具体故障及到 I 的见证。 |
| **Demo2 的错误出口** | 原配置通过。I 侧 prepend 从 2 改为 1 时排除该值，给出双故障中 `X→C→I` 到 Null0 的见证。保持 D 侧可接受的改配。 |
| **Demo3 的间接竞争** | 证实 B 的通告保持独立，Y 仍保留 B 和 T 两个输入并改选 B，Z 在相同场景下采用正确路径。对照将 B 的偏好降到 70，Z 下一跳可以保持 Y，但完整路径应改到 I。比较四设备与全量模型，并复查已有 276 组配置和故障的覆盖。 |
| **新候选被激活** | 增加一个最小用例，使原配置拒绝的路由在改配后出现。验证候选生成和剪枝能覆盖它，并检查它提供安全备选和它制造失败结果的两种情形。作为扩展策略开关前的验收。 |
| **同场景多个合法结果** | 在有两个合法结果的可控模型里，一好一坏必须拒绝，两条都好可以接受。再测某个故障下无合法模型，确认不会因反例查询空真而放行。作为多结果支持的验收。 |
| **故障与性质边界** | 覆盖无故障、恰好用满预算、下一档预算出现反例、断链、无路由、丢弃和环路。确认故障变量在所有设备使用相同的含义，并按性质定义识别实际交付。 |
| **输入和工具回归** | 覆盖缺失配置固定值、边界变量未连接、非目标字段残留、`UNKNOWN`、超时以及候选属性不受支持。运行副本的现有测试，保留旧语义已验证用例。 |

验证按三个层次进行：

1. **单元检查。** 校验目标配置释放、合法取值域、故障桥接、边界变量同一性、条件选择、量词和公式输出。新增测试优先覆盖能导致安全值被拒绝或错误值被放行的真实错误。
2. **模型等价检查。** 对小实例用同一配置域和故障预算构造全量参照。查询 Plus 公式与参照性质公式的异或，要求 UNSAT。对边界安全值和不安全值，另外给出可重复的求解查询。
3. **独立改配验证。** 用 Batfish/iBDP 重算测试配置的每个合法故障，对照选路节点、实际路径和交付结果。确定性案例可用此方式验证边界值及若干内部值。涉及 ECMP 或多个稳定状态时，还要用能够表达全部合法结果的参考模型验收。Traverse 用于已有语义回归或独立辅助验证，Plus 的验收公式由性质定义。

测试依据见 [Q1](../../../DEMOIDEA/demo1/Q1/README.md)、[Demo2 边界报告](../../../DEMOIDEA/demo2/result/forwarding/report.json) 和 [Demo3 竞争报告](../../../DEMOIDEA/demo3_fanout/result/competition/report.json)。

## 6. 评估设计

| 维度 | 要回答的问题 | 记录方式 |
|---|---|---|
| **正确性与完整性** | 有多少改配被错误放行或误排除？ | 对小规模完整域和独立改配集合记录误放行、误排除、模型无解和未知。分别报告保持原选路的安全值、换路后的安全值和会违反性质的值。大值域的精确比较使用公式异或。 |
| **切片效果** | 语义相关的设备和候选能否保留，切片能否节省求解？ | 比较全量模型、未过滤的设备拼接、经认证的依赖切片。记录设备、声明、断言、候选、边界公式和证明开销。同一场景检查竞争赢家、路径和性质。 |
| **规模与资源** | 性能随规模、故障预算和策略复杂度怎样变化？ | 用相同硬件、输入、预算和重复次数，分别改变设备数量、拓扑密度、起源数、竞争数和 `k`。分开记录生成、切片、边界认证、投影、化简、证据生成耗时和峰值内存，超时标出所在阶段。 |
| **解释和用户测试** | 人能否判断合理的配置变更，并说出原因？ | 记录允许公式的字段、原子、析取和嵌套数量，检验能否定位到配置行、竞争者、故障与路径。小规模预测试记录正确率、时间和错误类型。题目答案使用独立验证过的性质和见证。 |
| **流量扩展** | 安全换路会否因为拥塞被排除，权重能否弥补？ | 分开测试交付、容量、联合性质。先复现固定权重下的负载变化，再验证真实 SR 快照中路由字段与权重的联合范围。记录过载链路、故障、分流和背景流。 |

已有 [Router Scale 汇总](../router_scale/reports/router_scale_summary_20261110.txt)适合作为运行脚本与测量口径的来源。Plus 的规模结论使用新一轮同条件实测，分别报告输入导出失败、边界无法证明和投影超时。若进行用户测试，先冻结题目的性质、可编辑配置范围和独立答案。Q1 和 Demo3 适合检验安全换路及竞争影响，Demo2 适合检验错误出口。流量题等真实配置和交付语义对账完成后再入组。

## 7. 实施顺序和完成标准

1. **在 Plus 中打通正确性参照。** 先用现有协议方程为 Q1 和 Demo2 提供性质投影，复用现有字段映射和 SMT 工具。逐个核对安全换路与失败见证，并验证结果只含被释放的字段。
2. **接入经认证的依赖切片。** 让 Demo3 的四设备验收通过 Plus 的正式入口运行。检查新增切片与全量参照的性质允许区间等价，并用竞争对照证明保留了不变的候选。无法认证的切片使用更完整的设备语义继续求解。
3. **扩展路由和策略覆盖。** 先加入会激活新候选的策略开关，再分别验证 ECMP 和有反馈的多状态模型。每个新增范围先补全覆盖测试，再增加规模。逐故障重算主要用于验收和诊断，正常投影保持符号故障变量。
4. **接入 traffic flow。** 交付与容量共享路由和转发关系。先验证固定流量与权重，再加入真实 SR 权重联合求解。记录可达但过载的对照，并检查“无流量上链路”是否来自合法交付、丢弃或循环。

第一版完成时，Plus 入口应能复现 Q1、Demo2 和 Demo3 的结果，生成输入配置哈希、模型范围、边界证据、允许公式、见证及求解状态。已有用例保留可复查的回归结果。后续用户研究和流量求解以各自的验收证据为准。
